# Changelog: v3

Detailed release history for the `3.x` line.

## [3.34.0] - 2026-08-20

### Fixed — three transaction-correctness defects found in review

- **Cascades no longer run in parallel on a shared session.** `cascadePlugin({ parallel })` defaults to `true` and dispatched every relation through `Promise.allSettled`. Once cascades began propagating the parent `ClientSession`, that meant concurrent operations on ONE session — which MongoDB does not support, and which fails as undefined behaviour surfacing later as transaction-state errors on an unrelated statement, not as a clean error. `parallel` is now IGNORED when a session is present rather than obeyed: a throughput flag must not be able to corrupt a transaction. Outside a transaction the flag behaves exactly as before. Pinned by an ordering trace (row counts cannot tell sequential from parallel — both delete the same rows).
- **CAS filter authority: injected scope can narrow, never redirect.** `context.query` (hook-supplied tenant scoping / soft-delete filters) was spread LAST into the `ifVersion` match filter, so an injected `_id` retargeted the write to a different document and an injected version defeated the compare-and-set that is the branch's entire purpose. Scope is now spread FIRST and the caller's `id` + `ifVersion` last, on both the CAS write and the disambiguation read.
- **The CAS owns the version field exclusively.** A payload that also touched it produced one of two silent wrongs: Mongo rejected the whole update with a path conflict naming an internal field the caller never wrote (`$set`/`$unset`/`$rename` on `__v`), or the merge quietly overrode the caller's intent (`$inc: { __v: 5 }` became `1`). Such payloads are now refused up front with a message naming the reason; `$inc: { [versionField]: 1 }` stays legal because it states exactly what the CAS does anyway. The `ifVersion` path also picked up `assertNoMixedPatchShape`, the write-loss guard the claim paths already used.

### Fixed — capability declarations that contradicted behaviour

_(Not breaking: both flags described behaviour that never worked, so no correct code could depend on the old values.)_

- **`nestedTransactions` is now `false`, unconditionally.** It declared `true` (and derived `true` on any transaction-capable topology) by reasoning about the DRIVER, which does allow nesting on one session — while mongokit's own tx-bound proxy threw `Nested withTransaction is not supported` on the very same call. A capability is a promise to a caller who cannot see the implementation, so it must describe THIS repository. repo-core conformance now asserts the declaration against actual nested-call behaviour.
- **`capabilities.transactionRetry: 'managed'`** — declares that `withTransaction` retries INTERNALLY (the driver's convenient transaction API re-runs the callback on `TransientTransactionError` / `UnknownTransactionCommitResult` for up to 120s). repo-core's `retryingTransaction` previously wrapped it in a second 5-attempt loop: the callback's execution count stopped being bounded, telemetry saw a fraction of real attempts, and each outer attempt opened a new session. Callers now invoke it exactly once.

### ⚠ BREAKING (shipped in a MINOR) — Better Auth overlay is READ-ONLY by default

**This is the one change in 3.33.0 that can break a working host, and the version number does not signal it.** It ships as a minor deliberately: the previous behaviour was a security hole, not a feature, and holding the fix for a major would leave every host exposed for longer than the fix is disruptive.

**Who breaks:** any host calling `create` / `update` / `delete` (or any other write) on the repository returned by `createBetterAuthOverlay`, including via an arc resource that mounts write routes over it. Reads are unaffected.

**Symptom:** `ReadOnlyRepositoryError` naming the method and the remedy at the call site; under arc, a BOOT failure naming the routes instead — the write never reaches the database.

**Fix, one of:**
- Route identity mutations through `auth.api` (correct for essentially all application code — it is what preserves hashing, session revocation, org cascades, and plugin hooks).
- Disable the write routes on the resource: `disabledRoutes: ['create', 'update', 'delete']`.
- For genuine administrative repair paths only, pass `unsafeWritable: true` to the overlay and accept ownership of the invariants Better Auth would otherwise enforce.

**Why it was wrong:** `createBetterAuthOverlay` documented itself as a "read-side overlay" while returning a fully mutable repository, so `defineResource({ routes: ['create'] })` over `user` / `session` / `account` / `member` was one config line from writing rows Better Auth never hashed, cascaded, or fired a plugin hook for. A docstring is not a control. The repository is now sealed via repo-core's `asReadOnlyRepo`, and `capabilities.readOnly` lets arc refuse the routes at boot rather than surfacing the wall on the first request. Mirrors `@classytic/sqlitekit/better-auth`.

### Added — optimistic concurrency (`ifVersion` CAS) + transient-conflict classification (Phase 1b)

- **`update(id, data, { ifVersion })`**: the version predicate joins the match filter and the write `$inc`s the version — check and write are ONE round-trip, no read-then-write window. A STALE version throws `VersionConflictError` (409-shaped, from repo-core) with the actual version when cheaply available; **not-found stays `null`** — collapsing the two would invite a blind retry that clobbers the concurrent write. Operator-form payloads keep their operators; the `$inc` merges in.
- **`RepositoryOptions.versionField`** (default `'__v'`, mongoose's own versionKey — zero schema changes; note mongoose only auto-increments `__v` on array-mutating `save()`, so the CAS path `$inc`s explicitly). Capability `optimisticConcurrency: true`; repo-core's `ifVersion CAS` conformance block now EXECUTES here (fixture uses an explicit `version` field, exercising the option, not just the default).
- **`isTransientConflictError(err)`** on `Repository` — conservative classification (`TransientTransactionError` label / WriteConflict 112, never message text) consumed by repo-core's `retryingTransaction` envelope.
- **`withTransaction` passes the `TransactionHandle`** — callback receives `(txRepo, { session })` so outbox rows can join the transaction (repo-core 0.23 contract; conformance-pinned).
- Both CAS teeth are mutation-proven: dropping the `$inc` or collapsing stale-to-null each fails the conformance block.

## [3.33.0] - 2026-08-13

### Fixed — regex `flags` were dropped, silently downgrading every case-insensitive search

- `flags` is part of the filter IR (`FilterRegex.flags` in repo-core) and both Mongo compilers discarded it: the query compiler emitted `{ $regex }` with no `$options`, the expression compiler `{ $regexMatch: { input, regex } }` with no `options`.
- **Live impact, not theoretical.** Arc's CRUD list route normalises a parsed query through `toRepositoryFilter` → `policyRecordToFilter`, which correctly produced `{ op:'regex', pattern:'heritage', flags:'i' }` from BOTH parser shapes (mongokit's `/heritage/i` and arc's `{$regex,$options:'i'}`). The compiler then rebuilt the query without the flags, so `?name[like]=heritage` returned 0 while `?name[like]=Heritage` returned 3 — against an OpenAPI description promising "contains substring (case-insensitive)". Nothing errored; every operator search box just under-returned, and a lower-case search read as "no such record".
- Both compilers now carry `flags` through (`$options` / `$regexMatch.options`). `like` already honoured its case-sensitivity, so a `regex` node dropping flags also made the two forms disagree about the SAME filter depending on which compiler ran.
- Covered by `tests/filter-regex-flags.test.ts`; removing either passthrough fails it.

### Changed — dev toolchain

- `@classytic/repo-core` dev-dependency raised to `^0.22.0`, so the shared conformance suite's new `pages: 0` assertions actually execute here. They pass — 3.32.0 fixed that divergence — and are now ENFORCED rather than agreed by convention. Runtime peer floor unchanged.

## [3.32.0] - 2026-08-10

### Fixed — `aggregatePaginate` reported `pages: 1` for an EMPTY result; every other envelope says 0

- Two of the three offset-envelope builders computed `pages = Math.max(1, Math.ceil(total / limit))`, while `PaginationEngine` uses `calculateTotalPages` (a plain `ceil`). So a query matching nothing answered `total: 0, pages: 1` on the aggregation-IR path and `total: 0, pages: 0` everywhere else — two answers to "how many pages hold zero rows".
- This suite already asserted **0** for empty on both a plain offset read (`pagination-edge-cases`) and an aggregation pipeline (`pagination.test.ts` `aggregatePipelinePaginate`). The `Math.max(1, …)` sites were simply never exercised with an empty counted result, and drifted in that gap. The one test that asserts `pages: 1` has `total: 1`, where both formulas agree.
- Both sites now call `calculateTotalPages`, so ONE formula backs every envelope. **Behaviour change for callers reading `pages` on an empty aggregate result** (`1` → `0`): a `pages > 0` emptiness check keeps working, a `pages > 1` one is unaffected.
- **How it surfaced**, because it is not obvious from the code: a consumer resource added a `lookups` join to its list read, which routes the same query onto the aggregation path — and a golden wire fixture that had recorded `pages: 0` started failing. Nothing about that resource's own logic changed. Adding a join should not change the pagination envelope.
- Covered by a new `aggregate-ir` case (empty counted result ⇒ `total: 0`, `pages: 0`, `hasNext: false`), which is the combination that had no coverage.


### Fixed — `QueryParser` no longer rejects its OWN default sort (every list call 400'd)

- **`parse({})` threw on an EMPTY query** whenever `allowedSortFields` was configured without `createdAt`. `sort = '-createdAt'` was a DESTRUCTURING DEFAULT, so an absent `?sort=` became `-createdAt` and was then validated exactly like caller-supplied input — and since 3.25's fail-closed change, a blocked sort throws. The parser rejected the value it had just injected itself.
- The blast radius is every read on such a resource: `400 INVALID_QUERY_INPUT — Blocked sort field not in allowlist: createdAt`, on plain REST lists and on arc's MCP list tools alike, with **no request a caller could make to avoid it**. Present since **3.25.0**; it survived 2,797 tests because nothing combined a restricted sort allowlist with an empty query.
- The default is now applied only when the allowlist permits it (`isSortFieldAllowed`). A default the resource forbade is simply not applied — it is not a caller error and there is nobody to report it to.
- **Fail-closed behaviour is unchanged**: a sort the caller ACTUALLY sent still rejects. That distinction is the whole fix — 3.25 was right to reject caller input, and wrong to treat its own default as caller input.
- Multi-field defaults are all-or-nothing: a partially-applied default would silently reorder results rather than honour the declaration.
- Covered by `tests/sort-default-allowlist.test.ts` (6 cases: withdrawn when forbidden, applied when permitted, applied with no allowlist, explicit-bad still rejects, explicit-good passes, multi-field).

## [3.16.1] - 2026-06-18

### Fixed — update-body schema no longer carries `default` (PATCH data-loss hazard)

- **`buildCrudSchemasFromModel` / `buildCrudSchemasFromMongooseSchema` now strip every `default` keyword from `updateBody`** (recursively — properties, array items, nested subdocuments). A `default` has no place in a PATCH validator: hosts running Fastify/AJV with `useDefaults: true` (arc's `createApp` does) had the default **injected** into any update body that omitted the field, and the repository then `$set` it — silently overwriting stored data on a partial update. The canonical bite is a nullable field carrying `default: null` (e.g. `publishedAt`, `archivedAt`, a nullable `enum` price mode): a content-only save nulled it out. `createBody` still documents defaults (POST establishes a full doc); the nullable type-widening (`type: [..., 'null']`) stays, so a client may still explicitly send `null` — it just won't be auto-injected. Additive bug-fix; no API change.
- Replaces the per-app `stripDefaults` workaround that downstream services hand-rolled in their adapter factory. Covered by `tests/jsonSchema.generation.test.ts` ("update body strips defaults (PATCH safety)").

## [3.15.0] - 2026-06-06

### Added — `clearActiveOrganizationFromSessions` (Better Auth org-delete / member-removal integrity)

- **`clearActiveOrganizationFromSessions(sessions, organizationId, { userId? })`** in `@classytic/mongokit/better-auth` — nulls a dangling `session.activeOrganizationId`. Better Auth purges its `member`/`invitation` rows on org delete / member removal but never clears the session pointer, so a session left pointing at an org the user no longer belongs to makes `organization.getActiveMember()` return `MEMBER_NOT_FOUND` (and any frontend that trusts the pointer hangs — amplified by `session.cookieCache`).
- **Host-invoked, not arc-cascade**: arc's org cascade is DB-agnostic (purges through `@classytic/repo-core` adapters and must not touch a raw collection); the `session` collection is a Better-Auth/mongo concern this kit owns. Hosts wire it into `organizationHooks.afterDeleteOrganization` (org-wide; omit `userId`) and `afterRemoveMember` (one user; pass `userId`).
- **Structural by design**: takes a `SessionUpdaterLike` (`updateMany`) satisfied by both a native `db.collection('session')` and a Mongoose model — zero runtime mongoose/mongodb import (both stay peer deps). The adapter stores `activeOrganizationId` as a string, so the org id is matched as-is. Additive; no breaking change.

## [3.14.0] - 2026-05-17

### Added — `purgeByField` (compliance-grade tenant cleanup)

- **`Repository.purgeByField(field, value, strategy, options)`** implements `StandardRepo.purgeByField` from `@classytic/repo-core` 0.5.0. Powers `cascadeDeleteForOrganization` in arc — GDPR right-to-be-forgotten, SOX/HIPAA/PCI retention strategies, in one primitive.
- **Hexagonal split**: `runChunkedPurge` orchestrator (kit-agnostic, in repo-core) + per-kit `PurgePort`. Mongokit's port (`src/actions/purge.ts`, ~140 LOC) owns driver-specific decisions; chunk loop / signal / progress / retry / error envelope live once in repo-core.
- **Per-strategy round-trip optima**:
  - `hard` — `find({_id:1}).limit(n)` + `deleteMany` (2 RTs; mongo has no DELETE LIMIT).
  - `soft` — same shape with `$set: { deleted, deletedAt }`.
  - `anonymize` (static fields) — single `updateMany` per chunk.
  - `anonymize` (function-form replacers) — `bulkWrite` N heterogeneous `updateOne` ops in **ONE round-trip** per chunk (was N+1 before — measurable on multi-million-row anonymize jobs).
- **9 conformance scenarios pass** in `tests/integration/conformance.test.ts` (cross-kit parity with sqlitekit guaranteed).
- **Index requirement** is documented in the contract JSDoc: every cascading resource MUST have an index leading with the purge field, or chunks scan O(n²).

### Added — `sort` option on `Repository.getOne()` / `getByQuery()`

- Both methods now accept `{ sort }` to disambiguate when the filter matches multiple docs (FIFO claim, "latest pending"). Previous behavior dropped the option silently. New conformance test in `tests/repository.test.ts` locks in the contract.

### Improved — discoverability via error messages + JSDoc

- **`Repository.update()` JSDoc** now flags the raw-mongoose `Model.findOneAndUpdate()` anti-pattern (cross-tenant leak risk, audit gap, stale-cache bug), with side-by-side ❌/✅. Also calls out the CAS variant — `findOneAndUpdate({ _id, status: 'pending' }, { $set: { status: 'shipped' } })` is a compare-and-set; point at `repo.claim({ from, to })` instead. Includes the canonical 3-line host-side `updateAndMap` recipe (mongokit deliberately doesn't ship `updateAndMap` — mapper signatures vary too much).
- **`MongooseAdapter` constructor errors** now name the missing primitive (`new Repository(model)` from `@classytic/mongokit`) instead of "MinimalRepo instance". Detects common confusion: passing a Schema, passing the Model as the repository, etc. Tests in `tests/integration/mongoose-adapter.test.ts`.
- **`multiTenantPlugin` "missing context" error** now lists THREE ways to provide it: per-call `options.organizationId`, ambient `createTenantContext()` + `resolveContext`, or `bypassTenant: true` for cross-tenant admin/migration calls. Surfaces the existing ALS helper that hosts often grep for.

### Peer-dep range

- `@classytic/repo-core` peer bumped from `^0.4.2` → `^0.5.0` (consumes the new `TenantPurgeStrategy` / `PurgePort` / `runChunkedPurge` surface).
