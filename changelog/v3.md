# Changelog: v3

Detailed release history for the `3.x` line.

## 3.39.0

### Fixed — keyset index adequacy blessed the one shape that cannot serve the sort

The index-compatibility check stripped the `_id` tiebreaker before deciding,
on the stated grounds that an index covering the primary sort field "is still
efficient in practice — the planner uses the index for ordering and only pays
an in-memory tiebreak on duplicate primary values".

It does not. Measured against 20,000 rows with heavy ties on the sort field:

| index | blocking SORT | docs examined | returned |
|---|---|---|---|
| `{ tenantId, createdAt }` | **yes** | **20,000** | 20 |
| `{ tenantId, createdAt, _id }` | no | 20 | 20 |

A full sort of the matching range, paid again on every page — not a tiebreak.
Adequacy is now judged against the sort Mongo actually receives, the
recommended index names `_id`, and the warning says what happens without it.
`tests/integration/keyset-index-explain.test.ts` pins all of it through a real
`explain('executionStats')` rather than by assertion, because a unit test alone
kept passing for the entire life of the bug.

**This warns more than it used to, and correctly**: any schema whose keyset
index stops before `_id` was always producing that plan. The `stream()`
docblock's "O(1)" claim is now stated as conditional on the index, which is
what it always was.

### Fixed — a compound `topN` partition could merge unrelated partitions

Partition identity was `$toString` per value joined with U+0001, with null
mapped to the literal `'__NULL__'`. Both halves lose information:

```
('xyz', 'q')  and  ('xy', 'zq')   ->  both "xyzq"
(null, 'r')         and  ('__NULL__', 'r')    ->  both "__NULL__r"
```

Two unrelated partitions then ranked as one, so `topN` returned rows that were
not the top N of anything. Nothing errored — four rows across two partitions
came back ranked 1, 2, 3, 4.

Identity is now a **document expression**, compared value by value with no
serialization in between. An array would read better and is unavailable: Mongo
refuses it outright ("An expression used to partition cannot evaluate to value
of type array"). Keys are positional because a partition field may be a dotted
path. A missing field and an explicit null still partition together, as SQL's
`PARTITION BY` does; a real `'__NULL__'` string no longer joins them.

### Fixed — `bulkWrite` silently dropped driver options

The signature was `{ session?, ordered?, [key: string]: unknown }` and the call
forwarded exactly two keys, so `writeConcern: { w: 'majority' }` on a money
import type-checked, was dropped, and the write went out under the default
concern with nothing raised. The mongodb driver accepts an unknown option
silently too, so mongokit is the only layer that can catch it.

Supported options are now forwarded (`ordered`, `session`, `writeConcern`,
`bypassDocumentValidation`, `comment`, `let`, `ignoreUndefined`), and a driver
option this method does NOT forward is refused rather than ignored.

The fence is deliberately narrow: the options bag is also spread into
`_buildContext`, so plugins read `organizationId` and friends off it. A first
version refusing every unrecognised key broke multi-tenant `bulkWrite`
outright. Anything the driver does not know is context and passes through.

**What was NOT changed, because the claim does not hold:** a large `bulkWrite`
does not overrun MongoDB's command limits. The driver splits at
`maxWriteBatchSize`; 5000 operations insert cleanly, and a test pins that so it
does not get re-litigated into a chunking feature with partial-success
semantics nobody needs.

### Added — a rejected `createMany` reports what it wrote

```ts
try {
  await repo.createMany(rows);
} catch (err) {
  if (isCreateManyPartialError(err)) {
    err.partial.inserted;                    // documents that landed
    err.partial.failed;                      // { index, doc, code, message }
    await repo.createMany(err.partial.failed.map((f) => f.doc)); // retry only these
  }
  throw err;
}
```

**Neither ordering prevents a partial write.** `ordered: true` keeps everything
before the first failure, `ordered: false` keeps everything valid — measured on
a six-document batch with a conflict in the middle, ordered wrote 3 and
unordered wrote 5. Only a transaction gives all-or-nothing, and the default was
never the hazard.

The hazard was that the rejection carried no usable account of what happened, so
a caller treating it as "nothing was written" and retrying the batch
double-writes everything that had already succeeded. `partial.failed[].index`
is the load-bearing field: the driver reports failures positionally, and a
rejected document never comes back with an `_id` to match on.

Purely additive — `createMany` still rejects, with the driver's own error, so
every existing `catch` behaves exactly as before. `isCreateManyPartialError` is
exported for narrowing.

**`createMany`'s `ordered: false` default is unchanged**, deliberately. Two
reviews recommended flipping it to match the driver; the measurement above is
why it was declined. Flipping does not prevent partial writes, so it would be a
breaking change to a published package for a consistency improvement, sold as a
safety one.

### Fixed — a translated error dropped the diagnostics attached to it

`_handleError` replaces a driver error with the repository's contract (E11000
becomes a 409), and every property an action had attached went with it. The
`partial` report above arrived nowhere on its first implementation — the report
existed, its test failed, and the only evidence was the absence. Structured
diagnostics are now carried across the wrap explicitly; driver internals still
are not, which is the point of wrapping.

### Fixed — the overflow checkpoint meant "delivered", not "processed"

The resume token on the overflow error was recorded immediately before the
`yield`, so it said "handed to the consumer" rather than "the consumer finished
with it". If the buffer overflowed while the consumer was still processing the
event it held, a supervisor resuming from that token **skipped it** — delivered,
never processed, never seen again.

`watch()` now tracks both, and the error carries both:

- **`resumeToken`** — the last ACKNOWLEDGED event, set only when execution
  resumes after the `yield`, which happens when the consumer comes back for the
  next value. That is the only acknowledgement an async iterator can observe.
  Resume from this.
- **`deliveredToken`** — diagnostics only. Resuming from it reintroduces the
  loss.

Both are `undefined` when overflow arrives before the consumer completed
anything; the caller then restarts from whatever position it opened with.

The asymmetry is the point: resuming from the acknowledged token redelivers at
most the in-flight event, which an idempotent consumer absorbs. Redelivering
costs a duplicate; skipping costs a lost write. For money, inventory, outbox and
entitlement consumers those are not comparable.

`tests/unit/watch-backpressure.test.ts` pins the case that distinguishes them —
overflow arriving WHILE the consumer holds an unacknowledged event.

### Fixed — an unusable `maxBufferedEvents` silently removed the bound

The guard was `maxBuffered > 0`, which a negative, a fraction, `Infinity` and
`NaN` all slip past into unbounded buffering — the exact failure the option
exists to prevent, in a deployment that believed it had set a ceiling. Same
shape as the `countLimit` ceiling, and refused the same way: `0` remains the
documented explicit escape hatch, every other non-positive-integer throws.

### Fixed — `watch()` buffered change events without a bound

A change feed has no backpressure: the server pushes and the bridge held
whatever the consumer had not reached, so a consumer merely SLOWER than the
write rate was unbounded memory growth whose symptom — an OOM — appeared
nowhere near its cause. The drain also used `queue.shift()`, which is O(n):
measured at 200k entries, **68 seconds versus 2ms** for a head index.

- **`maxBufferedEvents`** (default 1024, `0` disables) bounds the buffer.
- Overflow **fails and never drops**, because a feed quietly missing a delete
  is a reconciliation mystery months later. The error carries the last
  delivered `resumeToken` as a property, so a supervisor restarts from a known
  position instead of parsing the message.
- Draining is O(1) per event, pinned by a scale-ratio test rather than a
  millisecond budget — a fixed threshold is what let the first version of that
  test pass with `shift()` still in place.

A change stream is an ingestion mechanism, not a durable queue; consumers that
must not miss events persist the token and stay idempotent.

### Fixed — a measure's `where` written in query syntax matched every row

`compileFilterToMongoExpr` returned anything that was not Filter IR unchanged,
described as "already an expression — pass through unchanged". A plain query
object is not an expression: `{ status: { eq: 'paid' } }` reaches `$cond` as a
non-empty object, which MongoDB evaluates as **truthy**. So a filtered measure
silently matched every row and came back equal to the unfiltered one.

Measured before the fix, over four rows with three distinct values:

```
countDistinct all = 3   where ne:'x' = 3   where eq:'x' = 3
```

The syntax is not imaginary — it is exactly what `AggRequest.filter` accepts,
because `compileFilterToMongo` runs `expandShorthands` over it. Two filter
surfaces on one request object, one honouring the syntax and the other quietly
ignoring it.

A `where` that is neither Filter IR, a boolean, nor a `$`-keyed aggregation
expression is now **refused**, naming what was passed and why it would have
matched everything. Not translated: a partial query-to-expression translator
would get the common operators right and fail the same silent way on the rest,
which is the failure being fixed.

### Added — `countDistinctStrategy: 'grouped'`, exact distinct without the memory ceiling

`countDistinct` accumulates the distinct values themselves and takes the size,
so a group's memory grows with the DATA rather than with the answer, and
MongoDB caps a group accumulator at 100MB. Fine over a status; a failure over a
user id, at the size the data reaches rather than one anyone planned for.

```ts
await repo.aggregatePaginate({
  groupBy: ['day'],
  measures: { users: { op: 'countDistinct', field: 'userId' }, revenue: { op: 'sum', field: 'amount' } },
  countDistinctStrategy: 'grouped',
});
```

`'grouped'` pre-groups by the distinct field so each distinct value becomes a
ROW, then counts rows. Rows spill; accumulators do not. Cardinality stops being
a memory question. `'accumulator'` remains the default because the extra
`$group` is not worth paying on small groups.

**Results are identical**, including the two semantics that are easy to get
wrong and were measured against `$addToSet` rather than reasoned about:

- a MISSING field is not a distinct value, but an explicit `null` IS. A naive
  `$group` disagrees on both, and answers `1` where `$addToSet` answers `0` for
  a group whose field is always missing. A `$type` check separates them.
- `where` excludes a row from the count without excluding it from the other
  measures — the `$$REMOVE` operand lands in the same "missing" slot, so one
  check covers both.

`tests/integration/countdistinct-strategies.test.ts` asserts the two strategies
**agree row for row** rather than asserting expected numbers, because the way
this goes wrong is a new path that is internally consistent and quietly
different. Removing the `$type` check fails five of those cases.

**It refuses what it cannot recombine.** Pre-grouping splits each group, and
only `count`/`sum`/`min`/`max` survive being recombined. `avg` (the mean of
means is not the mean), `percentile`, `stddev`, and a second `countDistinct`
are rejected at compile time with the alternative named — never approximated,
since a distinct count quietly within a few percent is the exact failure this
strategy exists to prevent.

### Changed — `countDistinct` documents its cardinality ceiling

It accumulates the distinct values themselves and takes the size, so every
distinct value in a group sits in that group's accumulator at once — fine over
a status, expensive over a user id. MongoDB caps a group accumulator at 100MB.
The measure type now states the ceiling and the three mitigations in order
(narrow the groups, `allowDiskUse`, or count distinct in its own request
grouped by the distinct field).

Deliberately no approximate mode: a distinct count quietly within a few percent
is exactly the plausible-looking wrong number this contract exists to avoid.

### Added — `cursorSecret`: HMAC-signed cursors

```ts
new Repository(Model, [], { cursorSecret: process.env.CURSOR_KEY });
// or, for repositories a kernel builds and a host never touches:
configurePaginationDefaults({ cursorSecret: process.env.CURSOR_KEY });
```

**What it protects.** A cursor is a position, and the server's own filters
decide what a caller may read — so a stolen cursor never crosses a tenant
boundary, and signing is not a substitute for scoping. What an unsigned cursor
gives away is the ability to MOVE the position: edit the encoded sort value,
re-submit, and the response says whether any row sorts past it. Repeat, and that
is a binary search over a column the caller can never read directly — "where do
salaries above X begin", against a list that only ever showed them names.

**What it does not.** The payload is still base64url JSON and still readable by
whoever holds the token, field names included. **Integrity, not
confidentiality.** Hiding which column a deployment sorts by needs encryption,
which this is not.

Four decisions that are the difference between this working and merely looking
like it works, each pinned by a test that fails when it is undone:

- **A configured secret makes a signature REQUIRED.** Tolerating an unsigned
  token "for compatibility" means an attacker strips the signature and walks
  past, while the setting still reads as enabled.
- **A bare ObjectId stops being accepted as a position.** `resolveCursorFilter`
  takes a raw 24-hex id as a fallback cursor, which carries no signature by
  construction — honouring it would have shipped the requirement with a
  documented bypass.
- **A key under 16 characters throws.** An unset environment variable reads as
  `''`, which would otherwise mean "signing on, key guessable", with nothing to
  say so.
- **Both cursor codecs are signed.** mongokit exposes two on the wire — the
  find-based keyset cursor and the aggregate-IR one. Signing only the first
  would leave a tamperable position on every aggregate keyset endpoint.

Comparison is `timingSafeEqual`. That one is guarded by a SOURCE assertion
rather than a behavioural test, because swapping it for `===` passes every
functional test there is — the falsification pass found nothing until the guard
was added, which is the definition of an unenforced capability.

**Rotation** takes a list: the first key signs, all of them verify, so a rollout
is deploy-new-first then retire-old. **Switching signing ON is a cutover** —
cursors already in flight carry no signature and are refused, and the client
restarts from page one. A "tolerate unsigned during rollout" flag would be a
permanent downgrade switch, so there isn't one. Switching it OFF is not a
cutover: signed tokens still decode, so a rollback breaks nobody.

### Added — `before`: keyset pages backwards

Keyset could only walk forward. A UI with a "previous" control had to keep
every cursor it had seen, or fall back to offset `skip(n)` for the way back.

```ts
const p2 = await repo.getAll({ sort, limit: 20, after: p1.next });
const p1again = await repo.getAll({ sort, limit: 20, before: p2.prev });
```

- **Rows come back in the order you asked for**, not reversed. `before: c` is
  "the page ending just before c", which is the same set as "the first `limit`
  rows after c in the opposite order" — so the query runs inverted and the page
  is turned back around before it is returned.
- The **cursor is validated against the sort it was minted under** while the
  PREDICATE is built in the walking direction (`resolveCursorFilter` gained an
  optional `buildSort`). Inverting both would reject every cursor as a sort
  mismatch.
- The envelope gains **`prev`** and **`hasPrev`** (`@classytic/repo-core`
  >= 0.28.0). Both cursors are minted under the caller's own sort, so either can
  be fed back as `after` or `before` regardless of which way the page was walked.
- **`after` + `before` together throws.** Two anchors describe two different
  pages; picking one silently returns a page nobody asked for.

`tests/integration/keyset-bidirectional.test.ts` pins the symmetry that matters:
forward to page N, back again, and you land on the page you came from — same
rows, same order, nothing gained or lost at the seam — for ascending,
descending and mixed-direction sorts.

### Changed — aggregate pagination no longer uses `$facet`

`$facet` puts every returned document AND the count inside ONE output document,
and no aggregation stage may exceed 16MB — so a page of large documents failed
outright with `BSONObjectTooLarge` instead of paginating. The only defence was a
warning above an arbitrary limit of 1000 telling the caller to go elsewhere.
`$facet` also cannot use an index for the stages inside it, so it was often the
slower plan as well.

The page and the count now run as two concurrent pipelines
(`countStrategy: 'none'` runs one). `tests/integration/aggregate-facet-split.test.ts`
fetches a ~24MB page — impossible to serve under `$facet`, and the falsification
run reproduces the executor error exactly.

**The trade, stated plainly:** two reads means a concurrent write can land
between them, so `total` may be a document out of step with `data`. That is
already true of the offset path — `paginate` runs find and count through one
`Promise.all` — so this makes aggregate consistent with it, and a count that is
one row stale is a far smaller defect than a page that cannot be fetched at all.

Applies to both `PaginationEngine.aggregatePaginate` and the standalone
`actions/aggregate.aggregatePaginate`.

### Fixed — keyset pagination silently dropped rows in three shapes

All three produced pages that looked correct on their own, which is why they
survived: the loss is only visible as a SET over the whole walk. The new
`tests/integration/keyset-mixed-direction.test.ts` asserts exactly that — every
document visited exactly once — for each shape.

**1. The caller's filter was replaced from page 2 onwards.** The position
predicate was merged by spreading (`{ ...baseFilters, $or: position }`), so a
query that carried its OWN `$or` lost it the moment a cursor was supplied:

```ts
repo.getAll({ filters: { $or: [{ status: 'active' }, { status: 'review' }] }, sort, after })
// page 1: both statuses.  page 2+: EVERY status — the filter was gone.
```

Same failure for a caller's `_id` filter (`{ _id: { $in: [...] } }`) when paging
by `_id`. The predicates are now composed under `$and` whenever a key collides,
and only spread when nothing does — so the flat shape every existing index hint
and explain plan was written against is unchanged.

**2. Mixed sort directions were rejected outright.** `{ priority: 1,
createdAt: -1 }` — the ESR-shaped compound index every MongoDB indexing guide
recommends — threw `All sort fields must share the same direction`. Nothing
about keyset requires that: the predicate is a tuple comparison whose operator
is chosen PER POSITION. The restriction pushed those callers onto the offset
path, i.e. onto `skip(n)`, which is the cost keyset exists to avoid. Mixed
directions are now accepted, and `_id` keeps whatever direction the caller gave
it (absent, it still follows the primary field, so existing callers are
unaffected).

**3. A nullable sort field ended the walk early.** BSON orders `null` (and a
missing field) below every typed value, and `$gt`/`$lt` never cross that
boundary — so `{ $lt: 0 }` does not match `null` and `{ $gt: null }` matches
nothing. Under `{ rank: -1 }`, where nulls sort LAST, the walk stopped at the
final typed row with `hasMore: false` and every null-valued document unread.
Each position now emits the branches its direction actually implies:

| direction | cursor value | predicate |
|---|---|---|
| asc | typed `v` | `{ $gt: v }` |
| asc | null | `{ $ne: null }` — every typed value follows null |
| desc | typed `v` | `{ $lt: v }` **or** `null` — nulls follow every typed value |
| desc | null | *(no branch)* — nulls are last |

A cursor past the last reachable row now matches nothing explicitly
(`_id: { $in: [] }`) instead of falling through to the unfiltered base.

### Fixed — cursor tokens are `base64url`, not `base64`

A cursor rides in `?after=`, and standard base64 puts `+` in the token — which a
query-string parser reads as a SPACE, so the cursor failed to decode unless
every client remembered to percent-encode it. The URL-safe alphabet has no such
character, and matches what `@classytic/repo-core`'s codec already emitted.
**Tokens issued under the old alphabet still decode** (Node's decoder accepts
both), so this is not a breaking change for clients holding one.

### Added — `allowDiskUse` on `aggregatePaginate`

A `$sort` or `$group` over more than 100MB fails with
`QueryExceededMemoryLimitNoDiskUseAllowed`. The IR path could already opt in via
hints; `aggregatePaginate` had no way to. Off by default: spilling to disk hides
a missing index behind a slow success, and MongoDB >= 6.0's own
`allowDiskUseByDefault` already decides for a caller that says nothing.

### Added — `countStrategy: 'capped'`, a bounded row count

`exact` walks every matching index key, on every page. That is right until a
filter matches enough rows for the count to outgrow the find it runs beside —
past which it is the dominant cost of a page the user reads fifteen rows of.
`none` avoids it entirely but leaves a list header with nothing to show, so
nobody adopts it for a screen that displays a total.

`capped` is the middle that products actually ship: stop the scan at a ceiling
and report the ceiling as a FLOOR. Elasticsearch's `track_total_hits`, Odoo's
limited `search_count` and GitHub's `1000+` are all this strategy.

```ts
const page = await repo.getAll({ page: 1, limit: 20, countStrategy: 'capped' });
// page.total             -> 10000
// page.totalIsLowerBound -> true      → render "10,000+"
```

- **`countLimit`** sets the ceiling per call; **`defaultCountLimit`** sets it per
  repository and on `configurePaginationDefaults` for the whole deployment
  (default 10000). A ceiling that is not a positive integer falls back to the
  library's rather than being honoured — `0`, a negative and `NaN` all reach
  `.limit()` as "no limit" somewhere in the driver stack, which would produce
  the unbounded scan the strategy exists to prevent while looking configured.
- **`totalIsLowerBound`** is reported, never inferred. `total === countLimit` is
  also what a collection of exactly that size returns, so a consumer cannot tell
  the two apart, and one that guesses renders `10,000+` over an exact 10,000
  forever. Absent on an ordinary page, so existing consumers see no change.
- **`hasNext` stays correct past the ceiling.** Once `total` sits at the cap it
  can no longer answer "is there more", so — like `'none'` — the page fetches
  `limit + 1` and answers from that. Deriving it from `page < pages` instead
  reports "no more results" in the middle of a collection: a wrong answer that
  looks like a right one. Pinned by `pagination-capped-count.test.ts`.
- Supported on `paginate()` (so every `getAll`) and `aggregatePaginate()` (via
  `$limit` before `$count` in the count facet). **`lookupPopulate` and the
  aggregate-IR offset path count exactly and SAY so** through the logger: they
  return repo-core's core envelope, which has no slot for `totalIsLowerBound`,
  and a bounded count nobody can identify as bounded is worse than an exact one.
  A deployment-wide `capped` policy keeps working there; the log line is what
  makes the path that ignored it findable.

Requires `@classytic/repo-core` >= 0.28.0 — before it, every count strategy
shared one `getAll` cache key, so a capped page could be served to a caller that
asked for an exact count.

### Changed — `CountStrategy` is declared once

The union was hand-copied into eight declarations, which is how the aggregate
variant had already drifted. It is now exported from `./types/pagination` and
referenced everywhere.

### Added — `./tenant`: the ONE `injectTenantField`, with index scope

`@classytic/repo-core/tenant` owns the tenant CONFIG. The Mongoose mutation that
config implies (add the field, lead every compound index with it) had no home,
so every kernel carried its own `src/models/inject-tenant.ts`: 38 copies at the
last count, drifting the way copies do. Some exempted TTL indexes from the
prepend and some did not; one (`order`) knew how to keep a global identity index
unscoped and the rest silently prefixed it; one (`revenue`) applied a host's
`extraIndexes` BEFORE the prepend, so a host could never declare an unscoped
index at all, while the kernel's own global indexes were declared by hand AFTER
the call, an ordering rule that lived only in a comment.

`@classytic/mongokit/tenant` is that implementation, once. `injectTenantField(
schema, tenant, { skipIndexes, indexes })` adds the field, prepends the tenant to
every declared index except one that already names it, a TTL index, or one named
in `skipIndexes`, then applies `indexes` honouring each `IndexDeclaration.scope`:
`'tenant'` (default) is led by the tenant field like the kernel's own; `'global'`
is kept as written, for an identity read that spans tenants by design (a buyer's
history across every seller, read with `bypassTenant`). A global declaration
must be named and must not name the tenant field, refused at describe time.
`declareIndexes` is exported for a schema whose field was injected elsewhere.

This is the seam PACKAGE_RULES P11.2 / 36.1 now require: a host declares the
indexes a kernel cannot know about on the blueprint, where they build and verify
with everything else, instead of a `collection.createIndex()` after bind that the
deploy step cannot see and the next `syncIndexes` drops.

### Fixed — a keyset cursor over a NESTED sort field resumed from `null`

The filter side always treated a sort key as a Mongo path
(`{ 'metadata.progressPct': { $lt } }`), but `encodeCursor` read
`doc['metadata.progressPct']`, a property no document has. The cursor carried
`v: null`, and page two was served by the null branch of the keyset filter: only
rows whose sort field IS null, with no error anywhere. `readSortValue` follows
the dotted path. `tests/unit/cursor-nested-path.test.ts`.

### Added — `configurePaginationDefaults`: a deployment-wide pagination policy

`PaginationConfig` is per REPOSITORY, supplied to a constructor. In a
kernel-composed app nobody constructs the repositories: a host wires engines
(`defineOrder`, `defineAccess`, `defineLms`, …) and each builds its own
internally. Unless every kernel grows and keeps a passthrough, a host has no
way to say "this deployment does not count rows", and inherits
`defaultCountStrategy: 'exact'` on every list endpoint it serves. That is an
O(matching rows) `countDocuments` on top of each page, paid again on every
page, for a total most screens do not display.

`configurePaginationDefaults({ defaultCountStrategy, defaultMode, maxPage })`
is settable once at boot and applies to repositories built before AND after
the call (the engine binds those three as getters). Resolution order is
unchanged where anything was said explicitly: per call → per repository → this
deployment default → the library's own. `getPaginationDefaults` reads it back,
`resetPaginationDefaults` restores the library defaults for a test.

### Fixed — a page past `maxPage` was a 500, not a 400

The page number comes from the querystring, so walking past the end is the
caller's mistake: a crawler, a fuzzer, a stale deep link. `validatePage` threw
a bare `Error`, which carries no status, so every framework above mapped it to
`internal_error` 500. The request was refused either way, but one of those
pages an on-call engineer and burns an error budget over `?page=999999`. It is
now `createError(400, …, { code: 'PAGE_OUT_OF_RANGE', meta: { page, maxPage } })`,
which matters most to a deployment that tuned `maxPage` DOWN for the skip cost,
since that is the one receiving the traffic.

## 3.38.1

### Fixed — an invalid id wedged the cache plugin's single flight

`getById` short-circuits a structurally invalid id (wrong ObjectId shape) to
`null` with no query. That fast path returned PAST `after:getById`, so
repo-core's single-flight claim taken in `before:getById` was never released:
the next identical read waited on it forever, with no error and no log. The
miss now fires the after-hook with `result: null` like every other miss.
`tests/cache-invalid-id-single-flight.test.ts` — the second read is raced
against a timeout; before the fix it never resolved.

### Changed — peer floor raised

- `@classytic/repo-core` `>=0.25.0` → **`>=0.27.0`**

## 3.38.0

### Added — `./indexes`: verify that a declared index actually exists

`unique: true` is a correctness constraint only if the index was BUILT, and a
skipped deploy step is silent. One deployment ran with 401 declared indexes
absent, accumulated duplicate rows on a "unique" field, and nothing said the
constraint did not exist. mongokit owns the declaration, so it owns the means to
check it.

`verifyIndexes(connection, { includeModel? })` returns
`{ modelsChecked, missingUnique, missingRegular, unreadable }`. Read-only — it
never builds; that belongs to a deploy step, not a serving process. Missing
UNIQUE indexes are reported separately because they have already been admitting
duplicates, while a missing regular one only costs a scan.

DELIBERATELY ONE-DIRECTIONAL: an index in the database but not in a schema is
NOT drift. Auth libraries and migrations manage indexes outside the ODM, and
calling those removable is what makes `syncIndexes()` unsafe.

Two storage-level subtleties are baked in, both of which made an earlier version
of this check report indexes that existed. A TEXT index is stored under an
invented `{_fts,_ftsx}` key with its fields in `weights`, so it is matched by
field SET. A single-field NUMERIC index is direction-agnostic — `{t:1}` and
`{t:-1}` are the same index. Tested against a real mongod, because neither is a
fact a mock can express; falsified by removing each.

`includeModel` exists because a kernel that materialises models per mode must be
skipped exactly as the deploy step skips it — indexing a model CREATES its
collection, so a mismatch reports permanent phantom drift.

Extracted from a host that had written it after the incident above. The second
host had no such check at all, which is the gap this closes.

## [3.37.0] - 2026-09-06

### Security

- ⚠ **BREAKING in a MINOR — `bulkWrite` sub-ops now obey soft-delete.**

  `softDeletePlugin` registered no `bulkWrite` hook, on the reasoning that a sub-op "isn't
  a single filter we can scope" — but each sub-op carries its OWN filter, which is exactly
  what the tenant plugin already walks. So on a soft-delete repository `bulkWrite` updated
  rows that had been deleted, and `deleteOne` / `deleteMany` HARD-deleted, destroying data
  the model says is recoverable. `tests/soft-delete-batch.test.ts`'s header claimed this
  case was covered; the file contained no `bulkWrite` test.

  `updateOne` / `updateMany` / `replaceOne` sub-op filters now carry the not-deleted
  predicate, and `deleteOne` / `deleteMany` sub-ops are rewritten to the same
  `$set: { deletedAt }` the dedicated handlers write. `insertOne` is untouched.

  `deleteMode: 'hard'` still bypasses, as on the single-document path — a purge is a
  deliberate physical delete. Code reaching `repo.Model.bulkWrite` directly (the purge
  path does) is unaffected, because it never enters the hook pipeline.

- ⚠ **BREAKING in a MINOR — `$and` branches are parsed instead of passed through.**

  `parseFilters` exempts `$or` and `$and` from the `$`-prefix operator block because both
  are legitimate compounds. `$or` is routed to `parseOr`, which re-parses every branch;
  `$and` was routed nowhere, so an array value fell to the direct-assignment branch and
  reached the driver verbatim. A caller could wrap anything this parser blocks in one:

  ```
  ?$and[0][$where]=sleep(1000)      → { $and: [ { $where: 'sleep(1000)' } ] }
  ?$and[0][$expr][...]              → passed through
  ?$and[0][name][$regex]=(a+)+$     → passed through, no regex budget
  ```

  Branches now go back through `parseFilters`, so the operator block, the field allowlist,
  the regex budget and depth limits all apply inside them, and a branch that parses to `{}`
  is dropped exactly as `parseOr` drops one — an emptied branch is match-all, and dropping
  the whole `$and` avoids the driver's "must be a nonempty array" error.

  Shipped as a minor because the old behaviour was a hole, not a feature. Two visible
  changes for callers: a `$and` carrying a blocked operator now throws under the default
  `invalidInput: 'throw'` instead of reaching Mongo, and values inside `$and` are now
  coerced (`{ 'qty[gte]': '5' }` becomes `{ qty: { $gte: 5 } }`), which fixes conjunctions
  that previously compared a string against a number and silently matched nothing.

  A parser configured with `allowedFilterFields` was never exposed — `$and` fails the
  allowlist check — and that behaviour is unchanged.

## [3.36.0] - 2026-08-30

### Changed

- ⚠ **BREAKING in a MINOR — the adapter's model and repository no longer share a document type.**

  `MongooseAdapterOptions.model` and `createMongooseAdapter`'s positional overload
  were `Model<TDoc>`, pinned to the same `TDoc` as `repository`. `Model<T>` is
  invariant in `T`, so a kernel whose repository speaks LEAN entities (string ids)
  could never hand over its own schema-inferred model, which carries hydrated
  documents — the two describe one collection and do not unify. Four downstream
  packages carried an `asEntityModel` cast solely to defeat this.

  Both now take `Model<TModelDoc>` with `TModelDoc` independent of `TDoc`. `TDoc`
  comes from `repository`, the data path. The adapter reads the model for
  `modelName` and `.schema.paths` metadata only, never for document typing.

  **What breaks:**
  - `MongooseAdapter.model` is now `Model<unknown>`, not `Model<TDoc>`. Reading a
    document type off it (`adapter.model.findOne().lean<T>()`) needs an explicit
    narrow. It was never true: `TDoc` is the lean entity, the runtime object is the
    hydrated model.
  - Code reading `options.model` back off a `MongooseAdapterOptions<T>` value sees
    `Model<unknown>`.

  **What replaces the lost static check.** Pinning both parameters to one `TDoc`
  incidentally cross-checked that the model and repository belonged together. The
  constructor now asserts that at RUNTIME against `Repository.Model`, throwing a
  named error on mismatch. That is strictly stronger — two different collections
  sharing a document shape were always statically indistinguishable — and it fires
  at composition, before any query runs. Repositories that expose no model (BYO,
  mocks) are not refused: absence of an answer is not a negative answer.

  This matters beyond typing: the adapter's model answers `hasFieldPath()`, which
  arc uses to infer an absent `tenantField`. A mismatched pair mis-answers that
  probe, and the query is either filtered to zero rows or left unscoped — neither
  of which errors.

## [3.34.0] - 2026-08-20

### Fixed — three transaction-correctness defects found in review

- **Cascades no longer run in parallel on a shared session.** `cascadePlugin({ parallel })` defaults to `true` and dispatched every relation through `Promise.allSettled`. Once cascades began propagating the parent `ClientSession`, that meant concurrent operations on ONE session — which MongoDB does not support, and which fails as undefined behaviour surfacing later as transaction-state errors on an unrelated statement, not as a clean error. `parallel` is now IGNORED when a session is present rather than obeyed: a throughput flag must not be able to corrupt a transaction. Outside a transaction the flag behaves exactly as before. Pinned by an ordering trace (row counts cannot tell sequential from parallel — both delete the same rows).
- **CAS filter authority: injected scope can narrow, never redirect.** `context.query` (hook-supplied tenant scoping / soft-delete filters) was spread LAST into the `ifVersion` match filter, so an injected `_id` retargeted the write to a different document and an injected version defeated the compare-and-set that is the branch's entire purpose. Scope is now spread FIRST and the caller's `id` + `ifVersion` last, on both the CAS write and the disambiguation read.
- **The CAS owns the version field exclusively.** A payload that also touched it produced one of two silent wrongs: Mongo rejected the whole update with a path conflict naming an internal field the caller never wrote (`$set`/`$unset`/`$rename` on `__v`), or the merge quietly overrode the caller's intent (`$inc: { __v: 5 }` became `1`). Such payloads are now refused up front with a message naming the reason; `$inc: { [versionField]: 1 }` stays legal because it states exactly what the CAS does anyway. The `ifVersion` path also picked up `assertNoMixedPatchShape`, the write-loss guard the claim paths already used.

### Fixed — capability declarations that contradicted behaviour

_(Not breaking: both flags described behaviour that never worked, so no correct code could depend on the old values.)_

- **`nestedTransactions` is now `false`, unconditionally.** It declared `true` (and derived `true` on any transaction-capable topology) by reasoning about the DRIVER, which does allow nesting on one session — while mongokit's own tx-bound proxy threw `Nested withTransaction is not supported` on the very same call. A capability is a promise to a caller who cannot see the implementation, so it must describe THIS repository. repo-core conformance now asserts the declaration against actual nested-call behaviour.
- **`capabilities.transactionRetry: 'managed'`** — declares that `withTransaction` retries INTERNALLY (the driver's convenient transaction API re-runs the callback on `TransientTransactionError` / `UnknownTransactionCommitResult` for up to 120s). repo-core's `retryingTransaction` previously wrapped it in a second 5-attempt loop: the callback's execution count stopped being bounded, telemetry saw a fraction of real attempts, and each outer attempt opened a new session. Callers now invoke it exactly once.

### ⚠ BREAKING (shipped in a MINOR) — Better Auth overlay is READ-ONLY by default

**This is the one change in 3.33.0 that can break a working host, and the version number does not signal it.** It ships as a minor deliberately: the previous behaviour was a security hole, not a feature, and holding the fix for a major would leave every host exposed for longer than the fix is disruptive.

**Who breaks:** any host calling `create` / `update` / `delete` (or any other write) on the repository returned by `createBetterAuthOverlay`, including via an arc resource that mounts write routes over it. Reads are unaffected.

**Symptom:** `ReadOnlyRepositoryError` naming the method and the remedy at the call site; under arc, a BOOT failure naming the routes instead — the write never reaches the database.

**Fix, one of:**
- Route identity mutations through `auth.api` (correct for essentially all application code — it is what preserves hashing, session revocation, org cascades, and plugin hooks).
- Disable the write routes on the resource: `disabledRoutes: ['create', 'update', 'delete']`.
- For genuine administrative repair paths only, pass `unsafeWritable: true` to the overlay and accept ownership of the invariants Better Auth would otherwise enforce.

**Why it was wrong:** `createBetterAuthOverlay` documented itself as a "read-side overlay" while returning a fully mutable repository, so `defineResource({ routes: ['create'] })` over `user` / `session` / `account` / `member` was one config line from writing rows Better Auth never hashed, cascaded, or fired a plugin hook for. A docstring is not a control. The repository is now sealed via repo-core's `asReadOnlyRepo`, and `capabilities.readOnly` lets arc refuse the routes at boot rather than surfacing the wall on the first request. Mirrors `@classytic/sqlitekit/better-auth`.

### Added — optimistic concurrency (`ifVersion` CAS) + transient-conflict classification (Phase 1b)

- **`update(id, data, { ifVersion })`**: the version predicate joins the match filter and the write `$inc`s the version — check and write are ONE round-trip, no read-then-write window. A STALE version throws `VersionConflictError` (409-shaped, from repo-core) with the actual version when cheaply available; **not-found stays `null`** — collapsing the two would invite a blind retry that clobbers the concurrent write. Operator-form payloads keep their operators; the `$inc` merges in.
- **`RepositoryOptions.versionField`** (default `'__v'`, mongoose's own versionKey — zero schema changes; note mongoose only auto-increments `__v` on array-mutating `save()`, so the CAS path `$inc`s explicitly). Capability `optimisticConcurrency: true`; repo-core's `ifVersion CAS` conformance block now EXECUTES here (fixture uses an explicit `version` field, exercising the option, not just the default).
- **`isTransientConflictError(err)`** on `Repository` — conservative classification (`TransientTransactionError` label / WriteConflict 112, never message text) consumed by repo-core's `retryingTransaction` envelope.
- **`withTransaction` passes the `TransactionHandle`** — callback receives `(txRepo, { session })` so outbox rows can join the transaction (repo-core 0.23 contract; conformance-pinned).
- Both CAS teeth are mutation-proven: dropping the `$inc` or collapsing stale-to-null each fails the conformance block.

## [3.33.0] - 2026-08-13

### Fixed — regex `flags` were dropped, silently downgrading every case-insensitive search

- `flags` is part of the filter IR (`FilterRegex.flags` in repo-core) and both Mongo compilers discarded it: the query compiler emitted `{ $regex }` with no `$options`, the expression compiler `{ $regexMatch: { input, regex } }` with no `options`.
- **Live impact, not theoretical.** Arc's CRUD list route normalises a parsed query through `toRepositoryFilter` → `policyRecordToFilter`, which correctly produced `{ op:'regex', pattern:'heritage', flags:'i' }` from BOTH parser shapes (mongokit's `/heritage/i` and arc's `{$regex,$options:'i'}`). The compiler then rebuilt the query without the flags, so `?name[like]=heritage` returned 0 while `?name[like]=Heritage` returned 3 — against an OpenAPI description promising "contains substring (case-insensitive)". Nothing errored; every operator search box just under-returned, and a lower-case search read as "no such record".
- Both compilers now carry `flags` through (`$options` / `$regexMatch.options`). `like` already honoured its case-sensitivity, so a `regex` node dropping flags also made the two forms disagree about the SAME filter depending on which compiler ran.
- Covered by `tests/filter-regex-flags.test.ts`; removing either passthrough fails it.

### Changed — dev toolchain

- `@classytic/repo-core` dev-dependency raised to `^0.22.0`, so the shared conformance suite's new `pages: 0` assertions actually execute here. They pass — 3.32.0 fixed that divergence — and are now ENFORCED rather than agreed by convention. Runtime peer floor unchanged.

## [3.32.0] - 2026-08-10

### Fixed — `aggregatePaginate` reported `pages: 1` for an EMPTY result; every other envelope says 0

- Two of the three offset-envelope builders computed `pages = Math.max(1, Math.ceil(total / limit))`, while `PaginationEngine` uses `calculateTotalPages` (a plain `ceil`). So a query matching nothing answered `total: 0, pages: 1` on the aggregation-IR path and `total: 0, pages: 0` everywhere else — two answers to "how many pages hold zero rows".
- This suite already asserted **0** for empty on both a plain offset read (`pagination-edge-cases`) and an aggregation pipeline (`pagination.test.ts` `aggregatePipelinePaginate`). The `Math.max(1, …)` sites were simply never exercised with an empty counted result, and drifted in that gap. The one test that asserts `pages: 1` has `total: 1`, where both formulas agree.
- Both sites now call `calculateTotalPages`, so ONE formula backs every envelope. **Behaviour change for callers reading `pages` on an empty aggregate result** (`1` → `0`): a `pages > 0` emptiness check keeps working, a `pages > 1` one is unaffected.
- **How it surfaced**, because it is not obvious from the code: a consumer resource added a `lookups` join to its list read, which routes the same query onto the aggregation path — and a golden wire fixture that had recorded `pages: 0` started failing. Nothing about that resource's own logic changed. Adding a join should not change the pagination envelope.
- Covered by a new `aggregate-ir` case (empty counted result ⇒ `total: 0`, `pages: 0`, `hasNext: false`), which is the combination that had no coverage.


### Fixed — `QueryParser` no longer rejects its OWN default sort (every list call 400'd)

- **`parse({})` threw on an EMPTY query** whenever `allowedSortFields` was configured without `createdAt`. `sort = '-createdAt'` was a DESTRUCTURING DEFAULT, so an absent `?sort=` became `-createdAt` and was then validated exactly like caller-supplied input — and since 3.25's fail-closed change, a blocked sort throws. The parser rejected the value it had just injected itself.
- The blast radius is every read on such a resource: `400 INVALID_QUERY_INPUT — Blocked sort field not in allowlist: createdAt`, on plain REST lists and on arc's MCP list tools alike, with **no request a caller could make to avoid it**. Present since **3.25.0**; it survived 2,797 tests because nothing combined a restricted sort allowlist with an empty query.
- The default is now applied only when the allowlist permits it (`isSortFieldAllowed`). A default the resource forbade is simply not applied — it is not a caller error and there is nobody to report it to.
- **Fail-closed behaviour is unchanged**: a sort the caller ACTUALLY sent still rejects. That distinction is the whole fix — 3.25 was right to reject caller input, and wrong to treat its own default as caller input.
- Multi-field defaults are all-or-nothing: a partially-applied default would silently reorder results rather than honour the declaration.
- Covered by `tests/sort-default-allowlist.test.ts` (6 cases: withdrawn when forbidden, applied when permitted, applied with no allowlist, explicit-bad still rejects, explicit-good passes, multi-field).

- Cascade delete correctness for tenant scoping, custom deleted-field names, and
  target hook execution.

## [3.5.5] - 2026-04-07

### Added

- Query primitives as dedicated subpath exports.
- `PaginationEngine.paginate({ countFilters })`.
- Better architectural guidance in `SKILL.md`.
- QueryParser schema-aware coercion and repository search modes.
- A documented plugin contract for external search backends.

### Fixed

- Dangerous `$or` sanitization edge cases.
- Numeric equality coercion inconsistencies.
- Search resolver plugin clearing behavior.

### Internal

- Replaced internal warning calls with the shared logger helper and further
  refactored QueryParser internals.

## [3.5.4] - 2026-04-07

### Added

- `softRequired` schema support for fields that are database-required but
  request-body optional.

## [3.5.2] - 2026-04-04

### Added

- `idField` support for alternate identifiers.
- `getOne(filter, opts)`.
- `findAll(filters, opts)` with sort support.
- `maxLimit: 0` as unlimited.

### Changed

- `createMany()` now defaults to `ordered: false`.
- Invalid ObjectId lookups now return miss semantics instead of surfacing a
  cast error.

### Fixed

- Plugin support for custom `idField`.
- Pagination defaults now respect `0` values correctly.

## [3.4.1] - 2026-03-31

### Added

- Compound keyset sorts.
- Collation support.
- Keyset pagination for `lookupPopulate`.
- `lookupPopulate({ countStrategy: 'none' })`.

### Fixed

- Lookup count inflation.
- Lookup field projection bugs.
- Uncorrelated lookup joins in several pipeline paths.
- Keyset cursor parsing and sort validation edge cases.
- Unbounded lookup counts and incorrect `$expr` blocking.

### Changed

- Raised the Node.js requirement to `>=22`.
- Tightened aggregate pagination typing.
- Improved `RepositoryInstance` typing and exported `CollationOptions`.

## [3.4.0] - 2026-03-31

### Added

- Soft-delete-aware batch operations.
- `parseDuplicateKeyError()`.
- Parallel pagination via concurrent find/count.
- Automatic lookup routing in `getAll`.
- Lookup field-selection shorthand.

### Fixed

- `updateMany` now respects hook-modified `context.data`.

## [3.3.0] - 2026-03-16

- `Repository.delete()` return typing and soft-delete response shape.
- Cascade hook registration race conditions.
- Several safety, cache, transaction, and custom-ID edge cases.

### Changed

- `CacheStats` now includes an `errors` counter.
- `DeleteResult` is the canonical return type for `Repository.delete()`.
